679 types, three kinds of relationship

Apple's FHIRModels generates every type in Sources/ModelsR4 from the FHIR StructureDefinitions, and the generator only ever expresses three relations in Swift: protocol conformance, containment by property, and one deliberately type-erased pointer. Learn those three and the other 126,000 lines are repetition.

Relation 1 — conformance

Two protocol lines, no class hierarchy

FHIR's spec has a base-class hierarchy; this port doesn't. There are seven protocols and 667 structs that conform to them — no subclassing anywhere. Which line a type sits on tells you what it is: something the server can address by URL, or something that only exists inside a parent.

Relation 2 — containment

A resource is one struct plus its private nest

Of 467 backbone structs, 459 are declared in the same file as exactly one resource and are used by nothing else — PatientContact belongs to Patient and cannot appear anywhere else. Only eight (Dosage, Timing, ElementDefinition, Population, ProdCharacteristic, ProductShelfLife, MarketingStatus, SubstanceAmount) are shared across resources.

Relation 2, continued — the shared core

Forty-one datatypes carry the whole module

The resources are wide but shallow; the reuse lives here. Two of these datatypes point at each other, and because a Swift struct cannot contain itself, that single cycle is why Reference and Identifier are the module's only classes.

How often each datatype is reached

Number of declared types that hold a property (or choice case) of that type, out of 679. Extension is on almost everything because every Element carries an extension array — it is plumbing, not modelling.

Relation 3 — the type-erased pointer

Reference does not say what it points to

658 properties across the module are references, and not one of them is parameterised by target. The Swift type is the same six fields whether it points at a Practitioner or at nothing that exists. The permitted targets live in the FHIR spec and, partially, in the generated doc comment above each property — never in the type system.

// both compile; only one is meaningful
patient.managingOrganization = Reference(reference: "Organization/42".asFHIRStringPrimitive())
patient.managingOrganization = Reference(reference: "Banana/42".asFHIRStringPrimitive())

Reference vs. contained vs. proxy

Three different ways one resource holds another. A Reference is a string pointer. DomainResource.contained and Bundle.entry.resource hold the real thing, wrapped in ResourceProxy — a 147-case enum with one case per resource type plus unrecognized, and the only place a resource literally nests inside another.

Where the targets actually are

The doc comment names a target often enough to be tempting and not often enough to trust — of 658 reference properties, most read like "Who and/or what this is about". Treat the spec, or your own mapper, as the source of truth.

The fourth thing, if you count it

186 nested enums stand in for value[x]

Where FHIR allows one field to hold any of several datatypes, the generator emits a nested enum — Observation.ValueX, Patient.DeceasedX. Nine of them are 50 cases wide, and in those, the 31 complex payloads are marked indirect to keep the enum's inline size small.

public enum ValueX: Equatable, Hashable, Sendable {   // Extension.value[x] — 50 cases
    indirect case address(Address)              // boxed: complex payload
    indirect case age(Age)                      // = Quantity
    case base64Binary(FHIRPrimitive<Base64Binary>)  // inline: primitive
    …
    indirect case usageContext(UsageContext)
}
